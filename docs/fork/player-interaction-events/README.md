## Implementation

Player notifications now follow the existing read-only pipeline:

`Player lifecycle → bounded observation → validated source transition → Director pending queue → optional event card → selected model`

- [`interactions.js`](../../../src/js/player/interactions.js) owns in-memory lifecycle counters and title normalization. Its callbacks publish data only. It contains no media, engine or device commands and no timers.
- [`player.js`](../../../src/js/player/player.js) reports genuine selection changes and confirmed media `playing`/`ended` transitions. [`app.js`](../../../src/js/app.js) records those facts and reports trusted Player-button openings. Existing play/pause, Script clock, transport gates and hardware rules are unchanged.
- The existing one-second AI projection carries an allowlisted `details.player`: browser-instance ID, three counters, workspace/video/playing booleans, title and title source. No file object, file key, source URL, directory or media bytes enter this projection.
- [`PlayerFacts`](../../../companion_ai/player_events.py), the closed observation schema and `BrowserObservation.event_evidence()` validate bounded facts, same-instance counter increases, source freshness and current state. Counter rollback is rejected. Initialization/reconnection/gaps do not establish a Player event.
- `ConversationService.enqueue()` uses the existing Director queue, occurrence ledger, capacity, TTL, debounce, user grace and reaction cooldown. Notifications have priority **20**; normal selection acknowledgements and essential session/mission/safety work retain their existing priority paths.
- At dispatch, a Player notification becomes an optional runtime card using the existing card prompt/grounding path, with `memory='none'`. It is outside the shuffled normal deck: no new deck lane, weights, scheduler or persistent card definition. The 48 personal Character Cards, 19 Common Cards and mission sequences remain byte-identical.
- Current Player facts and the concise event intention stay in the active provider user message. Existing card-only history separation keeps old requests/narrative excerpts in assistant-side background. There is no change to ordinary user-chat compilation.
- Safety and essential cards remain ahead of Player notifications. Pending Player notifications do not block Arrival; normal cards wait while a Player burst settles. Neither active dialogue generation nor background model curation is interrupted just to force a Player reaction. Session/observer epoch, selection/view and playback facts are checked again before delivery; superseded replies are discarded without treating the model as a controller.

The only new production text consists of event intentions, fact/provenance labels and grounding instructions. Companion dialogue is generated by the installed character model. Browser fixture responses are mocks for testing, not production dialogue.

## Events and exact triggers

| Event | Positive evidence | Exclusions / deduplication |
|---|---|---|
| `player_opened` | Trusted Player-button click changes closed → open, incrementing the opening counter | Initialization, layout mutation, refresh and programmatic opening do not increment it. Closing is silent; a later genuine reopening may react. |
| `video_selected` | Accepted local-file/URL selection changes the Player's existing media identity | Same-file/object reload, same URL, metadata/readiness refresh and script-only changes do not increment it. Clearing video invalidates old notifications without a new reaction. |
| `video_started` | Actual `playing` event with selected media, ready data, not paused/ended, and matching current resource | A Play click or rejected play is insufficient. Pause/resume, buffering and seeking retain the view latch. `ended` or a different selection resets that latch; the next confirmed playback may react. |

Local file identity reuses the Player's existing name/size/mtime comparison. URL identity remains internal. Only counters and a sanitized display label leave the Player. No hashing/upload/analysis of the video was added.

Titles use available supplied metadata when provided to the normalization helper; the current Player has no embedded movie-title reader, so local files/direct links use a **filename-derived label**. Normalization strips directories, URL queries/fragments, common extensions, control/format characters and underscores, and caps at 160 Unicode characters. Python validates/normalizes again. The model is explicitly told the source and that a filename does not verify movie identity. Titles are quoted untrusted data, not instructions. No frame/audio/participant images are supplied.

## Coalescing and priorities

The existing `selection_debounce_seconds` setting (default **2 seconds**) is also the Player settling window. Every fresh Player event resets that deadline. There is at most one pending Player candidate:

- Open → selection → confirmed start within the window becomes one `video_started` card with the latest verified title/context.
- Within the same media/view, confirmed start outranks selection, which outranks opening.
- A different new selection replaces a pending reaction to the old media.
- Closing, replacement, pause or a session/observer boundary can make a pending/generated reaction stale; it is then discarded.
- Opening, Arrival, missions and Closing keep their existing dedicated paths. Safety remains immediate and deterministic. Closing clears optional pending work; safety can cancel generation for its existing safety reason.
- The bounded browser observation buffer drops optional Player events before engine/safety events when full. Existing queue capacity, expiry, quiet/proactive settings, Event Intelligence enable/session-context-only choices and output pacing remain in force.

This is a settling window, not a promise to undo an utterance already delivered. Actions separated beyond the debounce/cooldown can produce separate reactions. Offline/initial-state interactions are not replayed later. Existing repetition checks still apply; a permitted new opening does not require another greeting.

### Quality assessment

This is an unblinded, single-assistant qualitative review of 28 outputs, not an independent or statistically powered reliability estimate. Scores: 2 = clear, 1 = weak/partial, 0 = failed/off-topic. Generic screen metaphors and explicit guesses/questions are not automatically counted as factual claims.
