# F2.6 narrative continuity

## Context audit and contract

F2.5.1 builds one ephemeral current-session block per inference after historical dialogue. `BrowserObservation.canonical()` supplies typed facts with known/current flags and source/kind: state, selected experience and goal, engine mode, elapsed time, sourced simulated/BLE BPM, thresholds, counters, device connections, calculated channels and unknown physical motion. Historical verified events carry evidence, session identity and age. The observer alone validates events; prose cannot add one. `ObserverDirector.context()` preserves canonical facts. Regular user requests use `render_facts`; deliberate selection/Came Early acknowledgements use focused connection/selection facts. Event JSON includes kind, priority, provenance/evidence and actual previous/current selections. Routine snapshots never become user dialogue.

Conversation memory defaults to eight messages, isolated by provider/endpoint/model, optionally persisted locally through SettingsStore. The native Ollama SYSTEM is prepended verbatim by the shared transport; runtime safety/output instructions supplement it. Character identity/personality comes from that SYSTEM, model identity from the provider, artwork identity from the manifest. No old story summary existed. Director topic/questions help scheduling/repetition checks but were not a separate durable story contract. F2.5.1 deliberately omitted older unsolicited replies from deliberate-event context and requested short acknowledgements; those constraints limited continuity. We also fixed a recent-event loop variable shadowing the request's actual trigger.

F2.6 adds one marked `NARRATIVE CONTEXT` JSON block, before current facts in the final transport turn. Version 1 contains a premise excerpt, advisory phase, up to four user-choice excerpts, three commitments, three recent developments and one unanswered-question excerpt. Each excerpt is at most 180 characters by default (configurable 60–240). Underlying lists are bounded to eight (configurable 2–12). These are fallible dialogue quotes, never authenticated measurements or reliable semantic summaries. Operational/physiological/numeric sentences are conservatively excluded. No second model call or new output grammar is used; when extraction fails, existing bounded dialogue and canonical facts remain. The expression header remains `[[expression:ID]]` with the existing twelve IDs.

A premise requires an explicit story/scene invitation. Phases change from choices and verified milestones/endings, never a timer. They guide context only, without advancing a scripted scene. The excerpt approach intentionally cannot reliably understand resolution of arbitrary promises, sarcasm or implicit choices. A real user turn clears the last-question scheduling block without claiming semantic comprehension. Operational history remains in the existing canonical contract; narrative never writes it.

## Memory and initiative

Narrative scopes use the same provider/endpoint/model key as dialogue plus the current session ID. New sessions clear anchors by default; switching away and back within the same session restores that model’s anchors. Only completed, accepted replies update story memory. Cancellation, reset and session/model changes cannot commit partial state. The authenticated, strict read-only `reset_narrative` message and Story memory UI reset anchors independently of dialogue/session records.

Local backend `narrative-config.json` in the existing private SettingsStore accepts `enabled` (true), `persist_between_sessions` (false), `max_excerpts` (8), and `excerpt_characters` (180). Cross-session persistence is explicit opt-in, sanitized on restoration; it never restores an old session identity, unanswered question or permission to initiate. No raw physiological time series is stored here. Disabling existing conversation memory also disables narrative injection/initiative. Existing dialogue persistence remains independent.

Director settings add `narrative_initiative_enabled` and `max_consecutive_unsolicited` (2). Global spontaneous/event opt-outs remain effective. Continuation requires a welcomed story, a choice/commitment, a fresh user turn not already used for initiative, no unanswered question, active session, fresh observer, no pending event, no active generation, user grace and existing global cooldown. A timer alone is insufficient. One opportunity is spent even on silence/failure, preventing retry loops. A continuation is a conversational opportunity, never an invented telemetry event. Important validated events retain priority; safety notices remain deterministic and independent. A quiet/stop/disengage request revokes initiative immediately.

## Candidates

Existing model sources, installed baseline models, artwork, drivers and safety logic are preserved. Experimental definitions are separately named `evelyn-narrative-v1` and `daisy-narrative-v1`. Evelyn copies the installed Lite source; Daisy copies the concise Daisy Lite source, preserving her established farm identity and avoiding the much larger Qwen baseline SYSTEM. Consequently Daisy comparison measures a source/style revision as well as narrative additions, not a single-variable experiment. Both retain the same locally installed base weights. New names map explicitly to existing Evelyn/Daisy portraits. No candidate becomes the application default.

## Validation

Results, reproducible evaluation commands, quality rubric and outstanding manual checks will be appended after regression and live evaluation. Manual user acceptance is deferred; automated checks cannot establish narrative quality.
